## Design Proposal

The starter repository mandates no programming language, framework, database, or API style. Everything below is a technical recommendation for PS-03, not an additional competition rule. The proposal assumes the MVP needs course/lesson delivery, assessment authoring, student attempts, and basic grading; validate scope against the official PS-03 brief before implementation.

### 1. Recommended Stack

- **Frontend:** React + TypeScript + Vite. Use React Router for pages and a small typed API client; keep styling in CSS modules or plain CSS to limit setup.
- **Backend:** Python 3 + FastAPI, with Pydantic request/response schemas, SQLAlchemy 2 for persistence, and Alembic migrations.
- **Database:** PostgreSQL. It supports relational constraints, transactions, and JSONB metadata for narrowly scoped audit details.
- **Authentication:** First-party email/password login with Argon2id password hashes and opaque, random server-side sessions in Secure, HttpOnly cookies. Store only a hash of each session token in the database. This avoids JWT refresh/revocation complexity for a browser-first MVP.
- **API:** Versioned REST/JSON under `/api/v1`; OpenAPI docs from FastAPI. Keep route handlers thin and enforce authorization in service/domain functions, not only in the UI.
- **Test tooling recommendation:** Pytest + HTTPX for backend; Vitest for frontend units and Playwright for a few end-to-end critical paths. No packages are being installed now.

Use a same-origin deployment or reverse proxy for frontend and API. This simplifies cookie and CORS policy. If hosting separately, use an explicit origin allowlist and credentialed requests, never wildcard origins with cookies.

### 3. Database Schema

Use UUID primary keys, UTC timestamps, foreign keys, and database constraints in addition to API validation. `PK` means primary key; `FK` means foreign key.

- **users**: `id UUID PK`, `email VARCHAR NOT NULL UNIQUE` (store normalized lowercase email), `password_hash TEXT NOT NULL`, `display_name VARCHAR NOT NULL`, `status VARCHAR NOT NULL CHECK (active|disabled)`, `created_at TIMESTAMPTZ`, `updated_at TIMESTAMPTZ`.
- **user_roles**: `user_id UUID FK users.id`, `role VARCHAR CHECK (student|instructor|admin)`, `assigned_by UUID FK users.id NULL`, `assigned_at TIMESTAMPTZ`; composite `PK(user_id, role)`. One account may have more than one role; normal signup can grant only `student`.
- **sessions**: `id UUID PK`, `user_id UUID FK users.id`, `token_hash CHAR(64) UNIQUE NOT NULL`, `csrf_hash CHAR(64) NOT NULL`, `created_at`, `expires_at`, `last_seen_at`, `revoked_at TIMESTAMPTZ NULL`. Index `(user_id, expires_at)`; expired/revoked sessions are rejected.
- **courses**: `id UUID PK`, `instructor_id UUID FK users.id`, `title VARCHAR NOT NULL`, `description TEXT`, `status VARCHAR CHECK (draft|published|archived)`, `created_at`, `updated_at`. Only an instructor/admin service action can publish or edit.
- **course_enrollments**: `course_id UUID FK courses.id`, `student_id UUID FK users.id`, `status VARCHAR CHECK (active|completed|revoked)`, `enrolled_at TIMESTAMPTZ`, `completed_at TIMESTAMPTZ NULL`; composite `PK(course_id, student_id)`. Enforce that the assigned account has the student role in the service layer.
- **lessons**: `id UUID PK`, `course_id UUID FK courses.id`, `title VARCHAR NOT NULL`, `body TEXT NOT NULL`, `position INT NOT NULL CHECK (position > 0)`, `status VARCHAR CHECK (draft|published)`, `created_at`, `updated_at`; `UNIQUE(course_id, position)`. Render lesson content as escaped text/Markdown, not trusted HTML.
- **assessments**: `id UUID PK`, `course_id UUID FK courses.id`, `created_by UUID FK users.id`, `title VARCHAR NOT NULL`, `instructions TEXT`, `status VARCHAR CHECK (draft|published|closed)`, `available_at TIMESTAMPTZ NULL`, `due_at TIMESTAMPTZ NULL`, `time_limit_seconds INT NULL CHECK (> 0)`, `attempts_allowed INT NOT NULL CHECK (> 0)`, `created_at`, `updated_at`; check `due_at IS NULL OR available_at IS NULL OR due_at > available_at`.
- **questions**: `id UUID PK`, `assessment_id UUID FK assessments.id`, `kind VARCHAR CHECK (single_choice|multiple_choice|short_answer)`, `prompt TEXT NOT NULL`, `points NUMERIC(7,2) NOT NULL CHECK (points >= 0)`, `position INT NOT NULL CHECK (position > 0)`, `created_at`, `updated_at`; `UNIQUE(assessment_id, position)` and `UNIQUE(id, assessment_id)` for assessment-scoped foreign keys.
- **question_options**: `id UUID PK`, `question_id UUID FK questions.id`, `text TEXT NOT NULL`, `position INT NOT NULL CHECK (position > 0)`, `is_correct BOOLEAN NOT NULL DEFAULT FALSE`; `UNIQUE(question_id, position)`. Return option text/IDs to students but never return `is_correct` before the attempt is submitted and results are released.
- **assessment_attempts**: `id UUID PK`, `assessment_id UUID FK assessments.id`, `student_id UUID FK users.id`, `attempt_number INT NOT NULL CHECK (> 0)`, `status VARCHAR CHECK (in_progress|submitted|graded|void)`, `started_at TIMESTAMPTZ NOT NULL`, `submitted_at TIMESTAMPTZ NULL`, `score NUMERIC(8,2) NULL`, `graded_at TIMESTAMPTZ NULL`; `UNIQUE(assessment_id, student_id, attempt_number)`, `UNIQUE(id, assessment_id)`. Enforce enrollment, availability, attempt limit, and one active attempt per student/assessment transactionally in the service layer.
- **attempt_answers**: `id UUID PK`, `attempt_id UUID NOT NULL`, `assessment_id UUID NOT NULL`, `question_id UUID NOT NULL`, `response_text TEXT NULL`, `points_awarded NUMERIC(7,2) NULL`, `feedback TEXT NULL`, `is_correct BOOLEAN NULL`, `updated_at TIMESTAMPTZ`; `UNIQUE(attempt_id, question_id)`. Composite `FK(attempt_id, assessment_id)` references attempts `(id, assessment_id)` and `FK(question_id, assessment_id)` references questions `(id, assessment_id)` so an answer cannot cross assessments.
- **attempt_answer_options**: `answer_id UUID FK attempt_answers.id`, `option_id UUID FK question_options.id`; composite `PK(answer_id, option_id)`. Validate that selected options belong to the answer's question and are not submitted for short-answer questions.
- **audit_events**: `id UUID PK`, `actor_id UUID FK users.id NULL`, `event_type VARCHAR NOT NULL`, `target_type VARCHAR NOT NULL`, `target_id UUID NULL`, `metadata JSONB NOT NULL DEFAULT '{}'`, `created_at TIMESTAMPTZ NOT NULL`. Append-only for security-relevant changes; never place passwords, tokens, answer keys, or unnecessary personal data in metadata.

**Relationships:** users have many role grants and sessions. Instructors own courses; courses contain lessons and assessments. Students join courses through enrollments. Assessments contain ordered questions and options. A student has numbered attempts for an assessment; each attempt has at most one answer per question and selected options through the join table. Audit events optionally identify an actor.

### 4. Roles and Permissions

- **Student:** browse published courses, enroll where permitted, view published lessons/assessments, create and submit own attempts, and see own released results.
- **Instructor:** manage only courses they own, publish their course material, create assessments/questions, view enrolled students’ attempts, and grade permitted responses.
- **Admin:** manage accounts/role grants and moderate courses. Admin access should be rare, audited, and not be a default signup role.

Use role-based checks plus resource ownership and enrollment checks. A role is not enough: every course, lesson, assessment, attempt, and result access must also check that the caller is authorized for that exact object.

### 5. Core Workflows

1. Student registers, verifies/login policy as available, and receives a session.
2. Student finds a published course, enrolls, then reads published lessons.
3. Instructor creates a draft course, lessons, and assessment; previews and publishes them.
4. Enrolled student opens an available assessment; server creates an attempt and returns questions without answer keys.
5. Student saves answers and submits; server validates ownership, time window, attempt state and attempt limit, then grades objective questions atomically.
6. Instructor reviews/grades short answers; student sees only their own results when released.
7. Admin disables accounts or changes role grants; these changes are audited.

### 6. Frontend Pages

- Public: login, registration, published course catalog, not-found/forbidden.
- Student: dashboard, course detail/lessons, assessment instructions, attempt-taking page, submission confirmation, results/history.
- Instructor: dashboard, course editor, lesson editor, assessment builder/question editor, attempt list, attempt review/grading.
- Admin: user/role management and course moderation. Keep the admin area minimal for the MVP.

Show actions based on role for usability, but always treat the backend as the authorization authority.

### 7. REST API Outline

All endpoints use `/api/v1`, JSON schemas, pagination for lists, and consistent errors.

- Auth: `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`, `POST /auth/csrf` if using a synchronizer-token bootstrap.
- Course discovery/student: `GET /courses`, `GET /courses/{course_id}`, `POST /courses/{course_id}/enroll`, `GET /me/courses`, `GET /courses/{course_id}/lessons/{lesson_id}`.
- Instructor course/lesson management: `POST /instructor/courses`, `PATCH /instructor/courses/{course_id}`, `POST /instructor/courses/{course_id}/publish`, `POST /instructor/courses/{course_id}/lessons`, `PATCH /instructor/lessons/{lesson_id}`.
- Assessment authoring: `POST /instructor/courses/{course_id}/assessments`, `PATCH /instructor/assessments/{assessment_id}`, `POST /instructor/assessments/{assessment_id}/questions`, `PATCH /instructor/questions/{question_id}`, `POST /instructor/assessments/{assessment_id}/publish`.
- Student assessment: `GET /assessments/{assessment_id}`, `POST /assessments/{assessment_id}/attempts`, `PUT /attempts/{attempt_id}/answers/{question_id}`, `POST /attempts/{attempt_id}/submit`, `GET /me/attempts`, `GET /me/attempts/{attempt_id}/result`.
- Instructor grading: `GET /instructor/assessments/{assessment_id}/attempts`, `GET /instructor/attempts/{attempt_id}`, `PATCH /instructor/attempts/{attempt_id}/answers/{answer_id}/grade`.
- Admin: `GET /admin/users`, `PATCH /admin/users/{user_id}/status`, `PUT /admin/users/{user_id}/roles`.
- Operations: `GET /health` (non-sensitive liveness only).

For all instructor/admin routes, service functions must check both role and ownership/scope. Student result routes must constrain by authenticated student ID; never accept a client-supplied student ID as authority.

### 8. Authentication and Authorization Design

Generate at least 32 bytes of cryptographically random session token on login; send it only in a `Secure; HttpOnly; SameSite=Lax` cookie and store its SHA-256 hash in `sessions`. Rotate on login/privilege changes, expire sessions, revoke on logout/password change, and reject disabled users. Use CSRF tokens on state-changing cookie-authenticated requests, plus SameSite cookies and Origin checking. Keep password reset out of the MVP unless a trustworthy email delivery path is available.

Authorize each request in this order: authenticate session, confirm active account, check required role, then enforce object ownership/enrollment and object state. Filter database queries by the caller’s permitted scope so unauthorized records are not fetched and serialized. Use database transactions for attempt creation/submission and role changes.

### 9. Security by Design

- **Passwords:** Argon2id with a maintained library and calibrated cost; never encrypt or log passwords. Generic login errors and rate limits on registration/login.
- **SQL injection:** SQLAlchemy bound parameters and ORM expressions; no string-built SQL. If raw SQL is necessary, bind every value.
- **XSS:** React escaping by default; do not use `dangerouslySetInnerHTML`. Sanitize any intentionally supported rich HTML with a maintained allowlist sanitizer. Add a restrictive Content Security Policy.
- **IDOR/BOLA:** central object-scope checks in services and scoped DB queries; test changing IDs across courses, attempts, answers, and results.
- **Validation:** Pydantic schemas with length/range/enum constraints; reject unknown fields where practical; enforce business invariants in both service logic and DB constraints.
- **Session/token:** opaque tokens, hash-at-rest, secure cookies, expiry/revocation, CSRF protection, no tokens in localStorage or URLs, TLS only.
- **CORS:** prefer same-origin. Otherwise allow exact trusted frontend origins; credentials enabled only for those origins, never wildcard `*`.
- **Headers:** HTTPS/HSTS in production; CSP, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, frame-ancestors in CSP, and a restrictive Permissions-Policy.
- **Errors:** stable error codes and request IDs; no stack traces, SQL, secrets, or existence-leaking details in client responses. Log diagnostic detail server-side with secrets/PII redacted.
- **Secrets:** environment-based settings, local ignored `.env`, example file with placeholders only, production secret store; never commit keys or production credentials.
- **Additional controls:** rate-limit public/auth endpoints, enforce request/body limits, keep audit events append-only, protect answer keys from API serialization, and apply least privilege to the database account.

### 11. Testing Strategy

- **Backend unit tests:** validation and domain rules, role checks, ownership checks, attempt windows/limits, objective grading, and result release.
- **API integration tests:** registration/login/logout/session expiry, course publication/enrollment, lesson access, assessment authoring, attempt submission, grading, and admin role changes against a disposable PostgreSQL database.
- **Frontend tests:** page-level role states, form validation, loading/error states, and answer submission/results rendering.
